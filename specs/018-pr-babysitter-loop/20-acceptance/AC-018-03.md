# AC-018-03: failing-check fixes are proposed by a separate implementer + verifier, never merged

## AC-018-03-01 — A failing check spawns a separate minimal-fix sub-agent
Given a watched PR with a failing check
When remediation is attempted
Then the loop spawns a separate minimal-fix sub-agent
And the fix is produced in an isolated worktree, never editing the PR branch in place

## AC-018-03-02 — A separate verifier confirms the fix
Given the implementer sub-agent's proposed fix
When the fix is evaluated
Then a separate verifier sub-agent independently confirms the change addresses the failing check
And no unrelated files were touched
And tests and lint still pass in the worktree
And the implementer never marks its own work done

## AC-018-03-03 — The loop proposes, never merges
Given a verified fix
When the loop acts on the PR
Then it proposes the fix as a patch or a PR comment
And it never merges the PR
And no auto-merge path exists

## AC-018-03-04 — The babysitter never changes CI gating
Given the loop running in this repo
When it reads the repository's CI
Then `.github/workflows/*.yml` is a read-only input
And branch protection is a read-only input
And the required-check policy is a read-only input
